Polars 2.0 shipped on 6 October, and its headline change is that collect() on a lazy query now runs on the streaming engine. The announcement gives row order as one reason that needed a major version, and the upgrade guide is clear that the streaming engine does not guarantee row order for joins, group-bys, and similar operations. What it cannot tell you is what that does to code written when order happened to hold. So I ran the same queries, with default settings, under Polars 1.44.2 (the last 1.x release) and 2.1.0 (the current release, out on 25 October). 2.0.0 gave the same results in every run I made before 2.1.0 shipped.

Under 1.44.2 every query matched its explicit-order version on every run. Under 2.1.0, 4 of the 5 were wrong on every one of the 20 runs, and for those 4 no two runs agreed with each other. The code did not change. Only the version did.

The data are two tables written to Parquet from R: 2,000,000 purchases in time order and 100,000 customers.

The audit joins them, runs five queries whose answer depends on row order, and compares each run with the same query written so the order is explicit. The same file runs under both versions.

# Run order-dependent Polars queries with default settings and compare each
# result with the same query written so the order is explicit.
import hashlib

import polars as pl


def queries(events, customers, explicit):
    if explicit:
        j = events.join(customers, on="customer_id", how="left", maintain_order="left")
    else:
        j = events.join(customers, on="customer_id", how="left")   # the default
    return {
        "first purchase per customer":
            j.group_by("customer_id").agg(pl.col("amount").first()).sort("customer_id"),
        "running total per customer":
            j.with_columns(running=pl.col("amount").cum_sum().over("customer_id"))
             .sort("event_id").select("event_id", "running"),
        "dedupe, keep first":
            j.unique(subset="customer_id", keep="first").sort("customer_id")
             .select("customer_id", "event_id"),
        "row index, first 1,000":
            j.with_row_index("i").filter(pl.col("i") < 1000)
             .select("event_id").sort("event_id"),
        "head(20)":
            j.head(20).select("event_id").sort("event_id"),
    }


def audit(events_path, customers_path, runs):
    ev, cu = pl.scan_parquet(events_path), pl.scan_parquet(customers_path)
    truth = {k: q.collect(engine="in-memory")
             for k, q in queries(ev, cu, explicit=True).items()}
    result = {"polars": pl.__version__, "runs": runs, "queries": {}}
    for name, ref in truth.items():
        wrong, outputs = [], set()
        for _ in range(runs):
            out = queries(ev, cu, explicit=False)[name].collect()     # default engine
            outputs.add(hashlib.sha256(out.write_csv().encode()).hexdigest())
            wrong.append(0 if out.equals(ref) else 1)
        result["queries"][name] = {"runs_wrong": sum(wrong), "distinct": len(outputs)}
    return result
res2 = audit(r.events_path, r.customers_path, runs=20)

Not much, which is the problem. Across 10 runs, the first purchase came back wrong for between 7 and 12 of the 100,000 customers. A share that small passes every eyeball check. The running totals were wrong on between 153 and 282 of the 2,000,000 rows, but a wrong one was off by as much as 1,212, in a column where the median purchase is 34. The row index was the loud failure: of the first 1,000 rows, between 961 and 1,000 were different rows from the ones 1.44.2 picked.

A small test fixture does not hide it. The same first-purchase query on synthetic logs of different sizes, 10 runs each:

    n_c = max(n_events // 20, 10)

On a thousand rows the error reaches up to 12% of the customers, so a test that compares output with a stored answer fails on every run. On ten million rows it is 28 to 44 customers out of 500,000.

Why it happens

The streaming engine splits the data into chunks and works on them in parallel. Operations that do not need order, such as a join, may hand chunks on in whatever order they finish. first(), cum_sum(), unique(keep="first"), and with_row_index() all read the order they are given, so they inherit the shuffle. head(20) came through intact here, but nothing promises that it will.

None of this is a bug. A Polars issue opened in November 2024 set out that left-join order should not be guaranteed, since it had only ever been an implementation detail, and the upgrade guide says the same thing about the new default. Code written against 1.x could rely on an order Polars never promised, and 2.0 is the first release whose default engine stops providing it.

The fix is one argument

import time

def first_q(join_order=None, expr=pl.col("amount").first()):
    if join_order:
        j = ev.join(cu, on="customer_id", how="left", maintain_order=join_order)
    else:
        j = ev.join(cu, on="customer_id", how="left")
    return j.group_by("customer_id").agg(expr).sort("customer_id")

ref = truth["first purchase per customer"]
variants = {
    "default": lambda: first_q().collect(),
    "join(maintain_order='left')": lambda: first_q("left").collect(),
    "sort_by inside the expression":
        lambda: first_q(expr=pl.col("amount").sort_by("event_id").first()).collect(),
    "collect(engine='in-memory')": lambda: first_q().collect(engine="in-memory"),
}
plan = [k for k in variants for _ in range(20)]
np.random.default_rng(7).shuffle(plan)           # interleave, so timing is fair
secs = {k: [] for k in variants}
wrong = {k: 0 for k in variants}
most = {k: 0 for k in variants}
for k in plan:
    t0 = time.perf_counter()
    out = variants[k]()
    secs[k].append(time.perf_counter() - t0)
    wrong[k] += int(not out.equals(ref))
    most[k] = max(most[k], int((out["amount"] != ref["amount"]).sum()))
for k in variants:
    print(f"{k:31s} wrong {wrong[k]:>2}/20   worst run {most[k]:>2} customers   "
          f"median {np.median(secs[k]):.3f} s")
## default                         wrong 20/20   worst run 14 customers   median 0.028 s
## join(maintain_order='left')     wrong  0/20   worst run  0 customers   median 0.028 s
## sort_by inside the expression   wrong  0/20   worst run  0 customers   median 0.035 s
## collect(engine='in-memory')     wrong 17/20   worst run  1 customers   median 0.044 s

Asking for order worked. Keeping the left table’s order in the join and putting sort_by() inside the expression both returned the right answer on all 20 runs. The join fix ran about as fast as the default here (median 0.028 against 0.028 seconds), so on this data it costs nothing. sort_by() is the more robust of the two, because the answer no longer depends on any upstream step keeping order.

Going back to the old engine was not enough. The upgrade guide offers collect(engine="in-memory") to restore the previous default, and it does restore the engine. It did not restore the order: on a Parquet source, 17 of the 20 runs still came back wrong, by at most 1 customer. Neither engine promises order, so the fixes that hold are the ones that ask for it. One more caution from the tracker: an optimizer bug that dropped maintain_order=True when a head() sat between a group-by and a sort (issue 30079) is fixed in 2.1.0, so upgrade before relying on maintain_order=True in that pattern.

Will your tests catch it?

from polars.testing import assert_frame_equal

bad = first_q().collect()
print("same shape:", bad.shape == ref.shape, "  same schema:", bad.schema == ref.schema)
## same shape: True   same schema: True
try:
    assert_frame_equal(bad, ref, check_row_order=False)
except AssertionError as err:
    print(str(err).splitlines()[0])
## DataFrames are different (value mismatch for column "amount")

A test that compares output with a stored answer will catch it, even one that ignores row order, because the values themselves differ. A test that checks shape, schema, or column names will pass.

R users are in the same position

data.table works through rows in the order it holds them, so amount[1L] by customer is the first purchase. DuckDB, which runs in parallel like the streaming engine, documents that first() can be non-deterministic without an ORDER BY. Same file, same question:

library(data.table)
library(DBI)
ev <- as.data.table(events)
truth_r <- ev[order(event_id), .(amount = amount[1L]), by = customer_id][order(customer_id)]

con <- dbConnect(duckdb::duckdb())
duck <- function(agg) dbGetQuery(con, sprintf(
  "SELECT customer_id, %s AS amount
   FROM read_parquet('%s') e LEFT JOIN read_parquet('%s') c USING (customer_id)
   GROUP BY customer_id ORDER BY customer_id",
  agg, normalizePath(events_path, "/"), normalizePath(customers_path, "/")))$amount

engines <- list(
  "data.table, amount[1L]" = function()
    as.data.table(customers)[ev, on = "customer_id"][
      , .(amount = amount[1L]), by = customer_id][order(customer_id)]$amount,
  "DuckDB, first(amount)" = function() duck("first(amount)"),
  "DuckDB, first(amount ORDER BY event_id)" = function() duck("first(amount ORDER BY event_id)"))
r_res <- t(sapply(engines, function(f) {
  bad <- replicate(20, sum(f() != truth_r$amount))
  c(runs_wrong = sum(bad > 0), most_customers_wrong = max(bad))
}))
dbDisconnect(con, shutdown = TRUE)
r_res
##                                         runs_wrong most_customers_wrong
## data.table, amount[1L]                           0                    0
## DuckDB, first(amount)                           17                    1
## DuckDB, first(amount ORDER BY event_id)          0                    0

DuckDB without an ORDER BY was wrong on 17 of 20 runs, and with one it was right on all of them. The rule is the same in every parallel engine: if the answer depends on order, say so in the query.

What this does not show

  • The data are a synthetic event log on one machine with 16 threads. How many rows go wrong depends on the thread count and on how the engine splits the work.
  • Polars 1.44.2 being right on every run shows what it did, not what it promised.
  • head(20) was right here. Nothing guarantees that either.

What to do on Monday

  1. Search lazy pipelines for first(), last(), cum_sum(), unique(keep=...), with_row_index(), and head() downstream of a join or a group-by.
  2. Add maintain_order="left" to the join that feeds them, or put sort_by() inside the expression.
  3. Do not count on engine="in-memory" to bring the old order back.
  4. Keep one test that compares output with a stored answer. check_row_order=False is fine.
  5. In SQL, write first(x ORDER BY t) or arg_min(x, t).

Whether someone else can rerun your pipeline and get your numbers is the replication standard, covered in A Guide on Data Analysis. The two scripts used here, audit.py and run_audit.py, sit next to this post.
